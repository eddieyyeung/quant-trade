## Context

`get_universe` 的两条路径（指数成分股、kline 回退）都用 `SELECT DISTINCT` 且不带 `ORDER BY`。DuckDB 的 DISTINCT 走哈希聚合，行序不保证，并行下每次都可能不同。

实测确认这确实是唯一的乱序源：

```
同一份有序 universe 连续调用三次 → picks 完全一致（策略本身确定）
reversed(universe)              → picks 全变（策略依赖入参顺序）
两次 get_universe               → 同集合、不同顺序
```

也就是说策略没有随机性，它只是把入参顺序当成了并列分数的打破规则。另外两处已确认**不引入**乱序：

- `_exclude_st`：`return [c for c in codes if c not in st_set]`，保序。
- `factor_ranking._apply_industry_constraint`：`industry_counts` 按 `codes` 插入建 dict，`keep` 按 `codes` 顺序取，最后 `selected[selected.index.isin(keep)]` 保持 `selected` 顺序。给定入参即确定。

## Goals / Non-Goals

**Goals:**

- 同参数、同数据、同进程或跨进程，`get_universe` 返回同一顺序。
- 下游在并列分数处的选择可复现——回测重跑得到同一组合，推荐与决策记录一致。

**Non-Goals:**

- 不改并列的**打破规则**本身。排序后并列按代码升序打破，这是一个任意但确定的约定；改成「按成交额」之类是另一回事，且会再次改变结果。
- 不改因子权重、行业上限、top-N 的任何取值——那会改变选股，与本变更无关。
- 不做「结果可复现」的全局保证：数据本身变了（重新同步、补历史），结果当然应该变。

## Decisions

### 决策一：在 SQL 里排序，而不是在策略里加 tie-break

**选择**：给两条查询补 `ORDER BY ts_code`。

**排除的方案**：在 `factor_ranking.generate_signals` 里给 `sort_values` 加稳定排序或按代码显式 tie-break。这能让策略对入参顺序免疫，但治不了别的消费方：`SnapshotBuilder._build_factor_ranking` 的 top-30 展示、任何未来直接吃 universe 的代码，都会继续受行序影响。乱序来自查询，就在查询处修。

**排除的方案**：两者都做。多一处改动就多一处改变结果的点，而效果完全重叠——排序后的入参顺序已经是按代码升序，显式 tie-break 得到的是一样的结果。

### 决策二：排序键取 `ts_code`，不取别的

代码是查询结果里唯一稳定且有全序的列。按调入日期、权重排序会把「行序稳定」和「业务含义」绑在一起，下次改动 `index_weights` 的语义时会连带打破可复现性。

### 决策三：接受存量结果可能变化

并列处的选股会变，已落库的回测/IC/训练集在那些位置与新结果不一致。

这是**修正**而非回归：此前的结果取决于一次未定义顺序的查询，谈不上「正确的那一份」。并列越多影响越大——因子缺失严重时（实测 8 个里 5 个为空）几乎全部选股都由行序决定，因子齐全时并列稀少、影响接近零。

不提供数据迁移：重跑得到的是一致的、可复现的结果，这本身就是收益。

## Risks / Trade-offs

- **存量结果与新结果不一致** → 不做迁移；在变更说明里讲明原因，避免被当成 bug 追。
- **确定性被误当成稳定性** → 排序只保证同一数据同一结果。数据变了（补历史、重新同步）结果当然变，这不是本变更能也不该保证的。
- **并列按代码升序是个任意约定** → 写进注释与 spec：它是确定的，但不是「更好」的。想按别的规则打破并列，是另一个变更。
- **仍有别的 SQL 可能无序** → 本变更只覆盖已被证实影响选股的两条。其余查询若进入选股链路，需要同样处理；不预先批量加 `ORDER BY`（无谓的排序开销）。
