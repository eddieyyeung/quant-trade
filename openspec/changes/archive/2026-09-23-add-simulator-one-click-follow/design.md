## Context

仿真决策台的手动路径已经稳定：`DecisionForm` 收「代码:百分比」文本 → `parseOrders` → `POST /step`。参考策略信号也已经算好并展示：`SnapshotBuilder._build_strategy_signals` 调参考策略 `generate_signals`，返回 `StrategySignalItem`（`ts_code` / `target_pct` / `direction` / `reason`），并为「跌出策略目标组合」的持仓自动补 SELL。字段与 `OrderRequest` 同构。

也就是说，缺口不是数据，是采纳路径：用户要照着只读表格把 15 段代码与权重手工敲进输入框。

两条约束值得在设计前摆出来：

1. **`resume` 已经算了两次全因子。** `Snapshot._build_factor_ranking` 遍历 `factor_registry.list_all()` 算一遍综合分，`factor_ranking.generate_signals` 为出信号再算一遍。任何新增的「重算一遍推荐」端点都会变成第三遍。
2. **`OrderRequest` 没有 `reason`。** `engine.py` 的 `reason=order.reason if hasattr(order, "reason") and order.reason else "用户主动建仓"` 因为字段不存在而恒走兜底分支——策略信号自带的「综合得分 2.31」到不了成交回执。

## Goals / Non-Goals

**Goals:**

- 决策台提供「按推荐方案」路径：预览将要执行的订单，再决定直接执行或回填表单微调。
- 信号到订单的映射落在服务层，而不是组件里。
- 采纳执行走的仍是既有 `POST /step`——涨跌停、T+1、停牌、现金与最小交易单位的规则一条都不重写。
- 订单携带理由，成交回执能看到这笔单子从哪来。

**Non-Goals:**

- 不展示「本周偏离推荐多少」。`Decision` 同时存了 `user_orders` 与 `strategy_orders`，偏离度离线可算，但那是对比视图的后续工作。
- 不给无参考策略的会话造兜底推荐（例如按 `factor_ranking` 等权）。权重凑 1 与现金约束会引入第二套口径，先不引入。
- 不动 `cash * 0.3` 单笔上限。它让 15 只等权组合的最后三笔被截断、实际投入约 93% NAV，但回测与仿真同款，改动会破坏对比口径。
- 不改输入语法。买入仍是「代码:百分比」，卖出仍是代码列表。

## Decisions

### 决策一：推荐订单随快照返回，而不是新开一个重算端点

**选择**：`Snapshot` 增加 `recommended_orders: list[OrderRequest] | None` 与 `recommendation_source: str | None`，由 `SnapshotBuilder` 在已经生成 `strategy_signals` 之后映射得到。前端读快照即可预览。

**排除的方案**：`GET /api/sessions/{id}/recommendation` 在点击时重算。它保证「看到的就是当前游标处的推荐」，但代价是第三遍全因子计算（见 Context 第 1 条）——因子策略每次进决策台要多等几秒，而收益只是一个页面加载后才可能变化的游标，而游标本来就由服务端 `step` 决定。等到真正执行时，`step` 内部还会再建一次快照，那次的信号同样与预览一致。

**排除的方案**：`POST /step` 带 `{"follow": "strategy"}` 让服务端直接生成并执行。省一趟请求，但没有预览——用户无法在执行前看到将要发生的换手，而这条路径的换手规模正好是最大的（满仓轮换）。

**为何映射不是「前端序列化」**：自动补卖（跌出目标组合的持仓补 SELL）属于领域语义，已经住在 `SnapshotBuilder` 里；映射函数跟着信号放在同一层，前端只做展示与转发。

### 决策二：映射保持「买入在前、卖出在后」，并保留补卖条目

信号列表本身是 BUY 在前、自动补 SELL 在后，映射不改顺序，与既有决策表单的提交顺序约定一致。

自动补 SELL 条目**原样保留**提交，而不是交给引擎的自动补卖去处理。两者结果等价——引擎的自动补卖循环在显式卖出之后才求值 `portfolio.holdings`，而 `Portfolio.sell` 清零时会删除该键，不会重复卖——但显式提交让 `Decision.user_orders` 完整记录「本周采纳了哪些卖出」，而不是留下一份需要靠引擎行为反推的记录。显式卖出还先于自动补卖执行，释放的现金更早进入买入池。

### 决策三：预览用 Modal，两个动作——执行与回填

Modal 里以表格列出代码、方向、目标权重与理由，并标出参考策略名；底部两个按钮：

- **执行**：把推荐订单原样 `POST /step`。订单带 `reason`。
- **回填到表单**：把订单写成既有语法填入买入/卖出输入框（买入 `代码:百分比`，卖出代码列表），并把备注预填为「按 <策略名> 推荐方案（已手工调整）」。用户可删掉不想跟的标的后提交。

回填这条路径是刻意的：每周全量跟随会让手动盘净值贴合策略净值，对比视图的逐周差异退化成「你做了一样的事」。真正的信息在部分采纳里，所以「采纳后编辑」必须是一等路径，而不是要用户自己抄。

回填会丢掉每单的 `reason`（输入语法没有理由位）——这是选它的代价，由备注里的来源标注补偿。直接执行路径不受影响。

### 决策四：无参考策略不显示入口，有策略但本周无信号显示禁用入口

`strategy_signals` 为 `null`（未配置参考策略）时不渲染按钮，既有的「无参考策略」提示已经解释原因。

为 `[]`（配置了策略、本周无信号）时**渲染但禁用**按钮并给出提示。静默隐藏会让用户以为功能坏了；禁用加说明能表达「这条路存在，只是本周没内容」。

这与既有 spec 对 `null` / `[]` 的区分保持一致。

### 决策五：`OrderRequest.reason` 可选，回执展示理由

`OrderRequest` 增加 `reason: str = ""`；`step` 的成交理由回落到「用户主动建仓」仅在该字段为空时。API 的 `step` body 解析可选 `reason`。

同时前端的成交回执要展示理由——只透传不展示等于没做。回执现在是「方向 代码 股数 @ 价格」，补上理由。

## Risks / Trade-offs

- **预览基于页面加载时的快照** → 两个标签页同时推进会让后推进的那个基于旧游标预览。这是既有行为（信号展示、持仓表都来自同一快照），不是本变更引入；执行仍以服务端游标为准，提交的是代码与权重而非游标，最坏结果是按旧组合换手。列入 Open Questions 观察，不在本次修。
- **`recommended_orders` 是 `strategy_signals` 的投影，快照里存在冗余** → 两者语义不同（前者是可直接提交的决策输入，后者是给人看的对照表），且投影逻辑在服务端单一处。若后续出现第三种消费方，再考虑合并。
- **回填丢理由** → 由备注的来源标注补偿；直接执行路径保留理由。
- **映射函数依赖信号的完整性** → `strategy_signals` 为 `null` 时映射结果也必须是 `null` 而不是空列表，否则前端无法区分「没策略」与「策略没说话」。由 `test_simulator_snapshot.py` 覆盖。

## Open Questions

- 对比视图是否要在后续补「偏离度」列（`Decision.user_orders` 与 `strategy_orders` 的差集）。本次不实现，但设计上不阻碍。
- 是否要给推荐方案一个仓位系数（例如全量权重 × 0.8 留现金）。会让「一键」多一个参数，暂不引入。
- **人工验证时发现：对比视图的策略侧目前是坏的，与本次变更无关，但会挡住上面那条的收益。** 两处独立缺陷：其一，`ComparisonEngine._run_strategy_shadow` 里的 `run_backtest` 抛 `Cannot compare Timestamp with datetime.date`，被 `except` 吞掉后返回 `(None, {})`，于是策略净值线根本不画；其二，同一函数**无论如何都返回空的 `strategy_holds_by_week`**（`return nav, {}`），所以「策略独有 / 共同」两列永远为空。结论：现阶段无论怎么采纳推荐，「对比视图里看到偏离」都做不到。这是独立变更的素材，不塞进本变更。
